# Historical Cash on Hand correction

The Admin calendar no longer has a minimum effective date. Initial historical setup and verified corrections use the actual business date. Settings remain append-only: the latest version for a given effective date takes precedence for new submissions until the next effective date. Earlier settings, physical counts, reconciliation snapshots and audit records are never deleted or rewritten.

Migration20 adds correction confirmation/review metadata and an Admin-only date-preview RPC. The preview displays the setting currently covering the date, the next setting date and saved cash entries in the affected interval. An overlap or saved entry requires an explicit second confirmation and an explanation of at least ten characters. A server-generated review token rejects stale confirmation after settings or relevant saved entries change. The insertion trigger recomputes and stores the review, verification source, actor and timestamp; the existing immutable audit trigger records the full old/new version. Client-supplied review details cannot override server results. Kiser's helper and existing RLS policies remain unchanged.

Existing saved reconciliations retain their original float, including a missing float snapshot. Changing a historical setting does not recalculate them. Managers can still correct physical counts using the original snapshot. The correction confirmation authorizes a new setting version only, not a rewrite of old cash records. Future first submissions for historical dates use the setting effective for that business date (morning entry date minus one). The missing-setting message is now exactly: "Cash on Hand not configured for this date."
