# Ownership Log wash goals release

Three goals persist per location independently of daily posts and calendar changes. They start read-only; Edit goals opens a draft with separate Save goals and Cancel controls. Daily post submission never saves goal drafts. Goal updates use the loaded updated_at value to reject concurrent overwrites. Saves stamp authenticated actor/time at the database.

The new daily field is WHAT WILL WE DO TODAY TO HELP ACHIEVE OUR GOALS. Existing Plan for Today remains. Original comments are neither rewritten nor deleted; recent history displays daily goal actions or legacy notes. Both Site Entry and Admin post editor use the same goals component.

Migration18 adds one nullable daily-action column and the per-location goals table, with RLS based on the existing Ownership Log location-access function. No existing security policies or records change. Anonymous access and authenticated delete/direct-trigger execution are denied.

Validation: 39 automated tests passed, including locked goals, explicit editing, Cancel, separate saves, optimistic conflict filter and failed saves. Both production builds passed; existing duplicate-title/bundle warnings remain. Rollback-only tm-ops-dev schema validation passed with RLS enabled and no anonymous read, authenticated delete or direct stamp execution. Dev lacks the Ownership Log baseline, so temporary baseline fixtures were used and all schema changes rolled back. Authenticated database role/write tests and full browser UI checks remain before production approval.

Release order: complete development integration/visual checks; verify production backup/schema and migration number; apply reviewed migration18 once after explicit approval; merge reviewed app and confirm automatic deployments; verify real daily action/goal saves using owner-approved values. Do not rerun earlier migrations. Rollback must keep goal, daily action and legacy comment data; reverting the UI can hide new fields but should not drop tables or columns.

No production changes, merge or deployment are authorized by this review PR.

## Persistence follow-up (October 19, 2026)

This follow-up branches from main at 414741b and reuses `ownership_wash_goals` from migration18. It does **not** introduce or apply a migration. The release order above describes the original feature only; do not reapply migration18 for this follow-up.

Code investigation found that structured Goal 1/2/3 fields already load and save by location, without any date or daily-post dependency. Site Entry nevertheless retained its initial location ID when Dashboard changed its single-location prop, so the goals component could remain attached to the previous site. The daily date also used the browser timezone and did not advance the form at midnight. The follow-up follows the supplied site, resets only daily fields on the site's date change, discards stale daily queries, and keeps the Admin goals component mounted while changing/backfilling post dates. Post load failures block submission rather than treating inaccessible posts as missing. Existing Store assignment filtering, Admin access, RLS, goal optimistic concurrency, and post edit windows remain in place.

Historical recovery: repository history before migration18 has only free-text `comments` in daily Ownership Posts, with no structured goal fields or documented encoding. Those comments are preserved and displayed as historical notes; daily writes omit `comments`. There is no safe automatic rule for splitting arbitrary prose into three goals or treating a backfilled post as the latest goal edit. Existing persistent rows, including intentionally blank goals, remain authoritative. No history is rewritten and no historical post is automatically promoted to goal storage. Recovery of a specific legacy comment requires confirming its intended goals and explicitly saving through Edit goals. Production schema/content could not be inspected: the connected Supabase account exposed only tm-ops-dev and rejected the production read-only metadata query. Thus the reported production daily clearing could not be independently reproduced, and production legacy recovery candidates are unverified.

Validation uses the actual JSX handlers with mocked hooks, clock and Supabase responses. It covers site-local day/year changes, daily field reset, missing posts, goal reloads, location switching (including Dashboard prop changes and out-of-order responses), explicit goal editing, historical post edits, and Admin backfills. These are component regression tests, not live authenticated browser/database tests. No production writes, migrations, merges or deployments are part of this PR.
